# 0134.1 — Enforcing the Engineering Rules

## Context

ADR 0134 set the rules and listed current violations from quick greps. Before
enforcing them, this thread measured the codebase properly. The measurement
changed three things:

1. **The violation table undercounted.** Core has 37 imports that point
   outward, not about 20.
2. **Most of those imports are not layering bugs.** They point at domain code
   that was filed in an infrastructure or utility folder, so the fix is moving
   files, not rewriting them.
3. **Write provenance depends on composition.** Attaching provenance needs the
   runtime's `home` and `getSourcePath`, which only composition holds. Doing it
   before Phase 3 would mean copying the same projection into every adapter
   (ADR 0134 R5.1).

This ADR records the audit, rules on the open questions, and sets the order of
work.

## Audit

Method: a scanner over `packages/server/src` (220 non-test files, 984 import
statements, covering static, type-only, re-export and dynamic imports) that
classifies each file into its ADR 0134 R1 layer. Paths are relative to
`packages/server/src/`.

### A1. Layer-to-layer counts

| Edge | Imports |
|---|---|
| core → core | 192 |
| core → infrastructure | 36 |
| core → utils | 1 |
| core → Node | 13 |
| infrastructure → core | 32 |
| infrastructure → adapter | 1 |
| cli → server | 3 |
| server → tools | 2 |

### A2. Violations of R1

- **Core imports Node IO:** 5 imports in 4 files. `node:fs` in
  `core/backlog-home.ts`, `core/config.ts`, `core/document-discovery.ts`, and
  `core/migrate-docs-native.ts`; `node:os` in `core/backlog-home.ts`. Core also
  uses `node:path` (6 files), `node:crypto` (1), and `node:util` (1). All three
  are pure.
- **Core imports outward:** 37 imports. 17 of them are the
  `IBacklogService` port, and the rest are listed in A3.
- **Infrastructure imports an adapter:** `storage/local/local-runtime.ts` →
  `server/tool-name-reservations.ts`.
- **Adapter imports another adapter:** `cli/runner.ts` →
  `server/local-app-request-runtime.ts` and
  `server/local-runtime-request-resolver.ts`; `cli/runner.types.ts` →
  `server/app-request-runtime.types.ts`; and `server/hono-app.ts` →
  `tools/index.ts` and `tools/register-substrate-intents.types.ts`.
- **Dynamic imports:** 2, both in `cli/index.ts`, loading the CLI's own entry
  points (`../node-server.js`, `./bridge.js`).

### A3. Misfiled domain modules

Each of these modules has no outward imports and no IO, and core depends on it:

| Module | What it is | Importers |
|---|---|---|
| `operations/types.ts` | `Actor`, `Mutation`, `MutationAttribution`, `OperationEntry`, `IOperationLog`: the domain's attribution types and the operation-log port | 65 files, 57 in core |
| `storage/substrate-storage-catalog.contract.ts` | the storage identity policy that substrates declare | 14 |
| `storage/storage-identity.ts` | formats and parses display ids from substrate claims (`node:path` posix only) | 6 |
| `memory/capture-rules.ts` | "Pure predicates; no side effects, no I/O" (its own header) | 3 |
| `memory/capture.ts` | writes episodic memories for significant events; called only from core | 3 |
| `resources/operations.ts` | applies text operations to content | 3 |
| `server/tool-name-reservations.ts` | the MCP names substrates may not claim | 4 |
| `utils/version.ts` | semantic-version comparison | 4 |

Real violations remain after moving these:

- the Node IO imports (A2);
- the `IBacklogService` port, which lives in storage and imports
  `storage/storage-adapter.ts` and `resources/manager.ts` types;
- `core/identity-resolution.ts` → `storage/local/git-runner.ts`, which is the
  `GitRunner` port type;
- `core/types.ts` → `resources/manager.ts`, the `ResourceContent` type;
- `core/wakeup.ts` → `memory/backlog-memory-store.ts`, where core constructs an
  infrastructure store as a fallback.

### A4. The shared request runtime

- `AppRequestRuntime` (`server/app-request-runtime.types.ts`) is the per-home
  service bundle. HTTP, MCP (through `ToolDeps`), and the CLI all consume it,
  and 15 files import it.
- `server/local-app-request-runtime.ts` builds that bundle. Its consumers are
  `server/dev-app.ts`, `server/local-node-app.ts`, and `cli/runner.ts`.
- **`resolveSourcePath` has no consumers.** MCP dropped it (ADR 0106.5 R8),
  and the CLI dropped it in `c460830`. `cli/runner.ts:108-111` still throws
  "Docs-native CLI runtime has no source-path resolver" when it is missing,
  so the CLI depends on a server policy it no longer uses.
- **`readLocalFile` is used, and should be.** It reads files inside the
  documents directory: identity and vision docs for MCP wakeup
  (`tools/backlog-wakeup.ts:132-138`), HTTP identity (`server/hono-app.ts:223`),
  and the resource route (`server/hono-app.ts:848`). Containment to the
  documents directory is correct for every consumer.
- `server/wakeup-grounding.ts` and `server/desk-grounding.ts` are imported only
  by the runtime builder and by each other. They are runtime readers, not HTTP
  routes.
- `validateLocalRuntimeSelection` is pure validation of the home selection.

### A5. What writes return

| Write | CLI output | MCP output | Home or file |
|---|---|---|---|
| create | `Created ID` plus a home line (0.75.0) | intent JSON `{ids, changed}` | CLI only |
| update | `Updated ID` | intent JSON `{ids, changed}` | none |
| delete | `Deleted ID` | text `Deleted ID` | none |
| edit | `Done` or a message; the result has no id | resource edit | none |
| remember | `remembered ID [layer] at …` | `RememberResult` JSON | none |
| forget | `Forgot N memories` | `{forgotten}` | n/a: a count, no documents |

- `tools/` never mentions `home_id` or `source_path`.
- The HTTP API attaches provenance on reads (`withEntityHomeProvenance`,
  8 call sites) and has no entity write routes.
- ADR 0129 R4 freezes the slug at creation, so a document's path never changes
  after it is written, and provenance for a write is just a lookup.
- All 14 CLI commands honor `--json`.

### A6. Can a test read the real filesystem?

`__tests__/helpers/setup.ts` mocks `node:fs` with memfs for every test.
`__tests__/identity-resolution.test.ts:54` shows the way around it:
`vi.importActual('node:fs')`.

## Rulings

### R1. The architecture test

- **R1.1** `src/__tests__/architecture.test.ts` reads the real source tree
  (A6) and checks every import (A1 method) against ADR 0134 R1.
- **R1.2** Core may import `node:path`, `node:crypto`, and `node:util`, because
  they are pure. `node:fs`, `node:os`, `node:child_process`, `node:net`, and
  `node:http` are IO.
- **R1.3** The allowlist lists exact `from → specifier` pairs. The test fails
  when an import is not allowed and not on the list. It also fails when a
  listed pair no longer exists, so a fixed violation must leave the list in
  the same change (ADR 0134 R6.2).
- **R1.4** `utils/` is a fixed set of files. Adding one fails the test
  (ADR 0134 R4.3).
- **R1.5 `server → tools` is a declared dependency, not a violation.** The MCP
  transport is served by the HTTP app (streamable HTTP), so the HTTP adapter
  mounts the MCP adapter. `tools` must never import `server`, and the test
  enforces that direction.

### R2. Move misfiled domain modules into core

Only the modules in A3 move. Code and exports are unchanged, and imports are
rewritten.

| From | To |
|---|---|
| `operations/types.ts` | `core/operation-log.contract.ts` |
| `storage/substrate-storage-catalog.contract.ts` | `core/substrates/substrate-storage-catalog.contract.ts` |
| `storage/storage-identity.ts` | `core/substrates/storage-identity.ts` |
| `memory/capture-rules.ts` | `core/memory-capture-rules.ts` |
| `memory/capture.ts` | `core/memory-capture.ts` |
| `resources/operations.ts` | `core/text-operations.ts` |
| `server/tool-name-reservations.ts` | `core/substrates/tool-name-reservations.ts` |
| `utils/version.ts` | `core/version-compare.ts` |

Moving the `IBacklogService` and `GitRunner` ports, and removing IO from core,
stays in ADR 0134 Phases 2 and 4, because each needs design work, not a move.

### R3. Composition

- **R3.1** `src/composition/` holds what every adapter shares for a local home:
  - `app-request-runtime.types.ts` (moved from `server/`);
  - `local-app-request-runtime.ts` (moved);
  - `wakeup-grounding.ts` and `desk-grounding.ts` (moved).
- **R3.2** `resolveSourcePath` is deleted: `createResolveSourcePath`, the
  `AppRequestRuntime` field, the `CliRuntime` field, and the throw in
  `cli/runner.ts`. It has no consumers (A4). `readLocalFile` stays in
  composition, contained to the documents directory. This retires ADR 0091
  §1 (`resolveSourcePath` injected into `ToolDeps`), which ADR 0106.5 R8 had
  already emptied of MCP consumers.
- **R3.3** `validateLocalRuntimeSelection` and its selection types move to
  `core/backlog-home-selection.ts`, next to `resolveBacklogHome`. They are
  renamed to the domain's words (ADR 0134 R2.1): `validateHomeSelection`,
  `HomeSelectionRequest`, and `ValidatedHomeSelection`. Nothing about them
  is specific to a local runtime or a request. The per-request registry,
  `LocalRuntimeRequestResolver`, stays in `server/` because it is HTTP's.
- **R3.4** After R3, the CLI imports nothing from `server/`.

### R4. Provenance on every write

- **R4.1** Core gets `describeDocumentLocation(provenance)`, which returns
  `project home ~/x: docs/tasks/TASK-0001-….md` or `global home: …`. It lives
  beside `projectHomeProvenance` in `core/home-provenance.ts`, because it is a
  display projection of the same domain object (ADR 0128, ADR 0134 R2.2).
- **R4.2** `composition/write-provenance.ts` exports
  `createWriteProvenance(runtime, homeDir)`, which returns
  `(id) => Partial<HomeProvenance>`. It is the only place that turns a written
  id into provenance. The CLI and MCP both get it from composition.
- **R4.3** One shape per result, following HTTP:
  - A result about **one** document is flat `HomeProvenance` (with
    `source_path`), like `withEntityHomeProvenance`.
  - A result about **several** documents (a compiled intent's `ids`) carries
    the home fields once, plus `documents: [{ id, source_path }]`.
  - All fields are additive (ADR 0134 R3.2).
- **R4.4** What each write gets:
  - CLI: `create` (moves to the shared helper), `update`, `delete` (the path is
    looked up before deletion), `edit` (by the id argument), and `remember`,
    each with the location line in human output.
  - MCP: compiled intents, `backlog_remember`, and `backlog_delete`, which
    keeps its text form and adds the location line.
  - `forget` is excluded, because it returns a count and names no documents.
- **R4.5** `ToolDeps` gains an optional `describeWrite` capability, injected
  where HTTP builds `ToolDeps` from the runtime. Tools never compute
  provenance themselves (ADR 0091, capabilities are injected).

## Validation

### Allowlist

| Rule | Start (1a) | After 1b | After 2 | After 3 |
|---|---|---|---|---|
| core-io | 5 | 5 | 5 | 5 |
| core-outward | 36 | 19 | 19 | 19 |
| infrastructure-adapter | 1 | 0 | 0 | 0 |
| adapter-adapter | 3 | 3 | 0 | 0 |
| frozen `utils/` files | 9 | 8 | 8 | 8 |

**48 known violations became 25** (plus 8 frozen `utils/` files). The
remaining 25 are the ones A3 names as needing design work: Node IO in four
core files, the `IBacklogService` port and three other types that core
imports from infrastructure, and `core/wakeup.ts` constructing a
`BacklogMemoryStore`. They are ADR 0134 Phases 2 and 4.

### The test catches what it should

A probe file in `core/` that imported `node:fs`, re-exported a CLI type, and
dynamically imported `server/hono-app.js`, plus a new file in `utils/`,
failed three checks: core-io, core-outward, and frozen utils. After each
phase, the ratchet failed until the fixed entries were removed, which is the
intended shrink-only behavior.

### Suite

- `pnpm --filter backlog-mcp typecheck`: clean after every phase.
- Server tests: 1476 after 1a, 1b, and 2 (no behavior change), and 1485 after 3.
- Root `pnpm build`: green.
