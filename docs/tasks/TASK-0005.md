Observed twice on 2026-07-18: W2's completion memory renumbered after colliding with main's MEMO-0003, then builder:telemetry-integrity and builder:desk-hardening both allocated MEMO-0006 in parallel worktrees (granite resolved by manual renumber to MEMO-0007 during rebase). Root cause: sequential id allocation is per-checkout with no cross-worktree coordination. This is a lattice-class problem (PROMPT 0003). Design space to explore BEFORE building: (a) merge-time renumber as documented protocol (current practice, works, manual); (b) allocation aware of family branches via W1 plumbing; (c) non-sequential ids for memories only. Needs an ADR ruling, not a quick patch — file under the lattice thread.

## 2026-09-08 investigation — distinguish home and family consistency

The duplicate MEMO-0016 observed while recording the mainline workflow was a
same-home stale-runtime failure, distinct from the worktree merge collisions
above. [ADR 0133](../adr/0133-atomic-document-creation.md) fixes that class with
atomic repository creation, fresh identity claims, and a home-local write lock.
Four independent HTTP/MCP processes successfully created twenty concurrent
memories with unique IDs and matching journal entries.

This task stays open for **family-wide allocation**. The existing W1 family
probe is a fail-open read aid and excludes main checkouts/detached HEADs; it
cannot silently become allocation authority. Decide shared sequence reservations
versus branch-qualified IDs, including bootstrap from existing histories,
independent clones/offline writes, and recovery, before implementation.
